Monomem README demo - ground truth (1.7.0)
==========================================

Everything in docs/monomem-demo.gif, docs/brand/monomem-demo.mp4 and the three screenshots
(docs/brand/screenshot-*.png) comes from this run. The earlier 1.5.0/1.2.0 transcript is replaced.

Recorded:  2026-11-20
Version:   monomem 1.7.0 (the published npm package, installed into a scratch folder; not the repo checkout)
Platform:  win32, Node v24.18.0, Chrome (Playwright 1.56.1) for the dashboard screens
Stores:    two throwaway stores, each under a temp folder (MONOMEM_HOME=...tmp-mm17/home and home2), 127.0.0.1,
           ports 18890 and 18891, deleted afterwards. The real store was never opened.
Writers:   tokens.json with claude-code (write), cursor (write), gemini-cli (read), admin.
           written_by is stamped by the server from the token's label.

How the film is made (what is cosmetic)
---------------------------------------
* The dashboard panels are real full-resolution screenshots of the 1.7.0 dashboard, taken with real clicks
  (search, Held tab, Reject, Confirm reject, Activity tab).
* The terminal panels show the real REST responses (fields shown are copied from them). The text is typed out
  on screen and the film switches between steps; waiting time between steps was cut. Nothing else is sped up.
* The gold rings are drawn over the real screens to point at the button being clicked.
* The dashboard "deploy target" screen is shown from 2.7 s on, after the save step; it was captured after the
  real save.
* No Cursor, Gemini CLI or Claude Code client was run: the three names are separately authenticated tokens
  against one store, which is the claim. The pane labels are the app names the writers stand in for.
* Latency is client-side wall clock for one loopback fetch(), so it includes Node's HTTP client overhead.

Store 1 (digest and tidy marks)
-------------------------------
This store holds six notes, the same held write, and captured sessions sent through POST /capture as the capture
hooks do: nine sessions that ran tools (most with a WebFetch result, one with a curl command), plus two sessions
whose start date and outside-read mark were reset directly in the throwaway database (start 2026-10-28, mark empty)
so they look like sessions recorded before the mark existed. That reset is the only hand edit; without it
`monomem tidy marks` correctly prints "Nothing to stamp". The sessions and the fetches are made up for the demo, so the
percentage (7 of 9) describes the demo data, not typical use.

$ monomem tidy marks
  session 7f3a9c21: last outside read 2026-11-20T22:55:51.051Z
  session c08e41d7: last outside read 2026-11-20T22:55:51.079Z
DRY RUN: nothing was changed. 2 ended session(s) would be stamped. Open sessions are never touched. Run `monomem tidy marks --yes` to apply (a backup first: `monomem backup`).

* "Too few sessions for a steady rate" is part of the real digest text; with nine demo sessions it is the right thing for it to say.
